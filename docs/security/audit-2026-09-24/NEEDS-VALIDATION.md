## 1. Anonymous 'Passwort vergessen' request overwrites a pending Nutzer's 7-day Initial-Zugang token with a link that is never delivered, blocking account activation

`backend/src/auth/auth.service.ts:passwortVergessen:overwrites-initial-access-token`

**Beschreibung.** When an authenticated Nutzer creates a colleague, NutzerService.createNutzer gives the account a random placeholder password (nutzer.service.ts:29) and mussPasswortSetzen=true. It stores the SHA-256 hash of a 7-day setup token in Nutzer.passwortSetzenToken/passwortSetzenTokenAblauf (nutzer.service.ts:39-41). The raw link is returned once, only to the creator (nutzer.service.ts:52). The unauthenticated POST /api/v1/auth/passwort-vergessen (auth.controller.ts:75-80, @IsEmail DTO, 5/min throttle) finds any Nutzer by email (auth.service.ts:32). It then writes a new token hash and a 1-hour expiry into the same columns without any condition (auth.service.ts:39-45). The column is shared by design (schema.prisma:37-38). The request does not check mussPasswortSetzen and does not keep a still-valid token. The new raw token goes to the Mailer, and the only bound implementation is ConsoleMailer (auth.module.ts:34). ConsoleMailer ignores the link and only logs the recipient (mailer.ts:13-16); the code comment says SMTP is not yet connected. After the overwrite, the creator's link hashes to a value no row holds, so passwortSetzen throws 'Link ist ungültig oder abgelaufen.' (auth.service.ts:51-55). The pending account cannot log in, because its password hash is from a random UUID. The source has no reissue route: NutzerController only has POST /nutzer and GET/PATCH /nutzer/me. Recreating the account fails because email is @unique (schema.prisma:23). The seed script only runs when no Nutzer exists (seed-initial-nutzer.ts:23-25). Recovery therefore needs an operator to edit the database, and the attacker can repeat the request afterwards. The attacker needs only the target's email address, which is often a predictable company address, and one request. The request also replaces pending reset tokens of established users. Those users lose nothing real, because the ConsoleMailer never delivers their reset links either. The impact is limited to account availability, specifically onboarding. It gives no credential disclosure or takeover.

**Behauptete Ursache.** The Initial-Zugang and 'Passwort vergessen' flows share a single passwortSetzenToken/passwortSetzenTokenAblauf slot. AuthService.passwortVergessen overwrites that slot for any existing email without checking mussPasswortSetzen or whether a still-valid Initial-Zugang token exists. The replacement token is only handed to the non-delivering ConsoleMailer, and no authenticated reissue path exists. An anonymous caller can therefore revoke a pending account's only working credential path.

**Trace**

- *entrypoint* `backend/src/auth/auth.controller.ts:78` (AuthController.passwortVergessen): Public POST /api/v1/auth/passwort-vergessen (decorators at lines 75-77). No JwtAuthGuard, 5 requests/min throttle, and the body is only validated as @IsEmail (dto/passwort-vergessen.dto.ts).
- *propagation* `backend/src/auth/auth.service.ts:32` (AuthService.passwortVergessen): prisma.nutzer.findUnique by email. Every existing Nutzer proceeds, including accounts with mussPasswortSetzen=true, which are not filtered.

- *sink* `backend/src/mailer/mailer.ts:16` (ConsoleMailer.sendPasswortSetzenLink): The only bound Mailer discards the new raw link (the _link parameter is unused, line 13) and only logs the recipient. No usable token reaches anyone, and the creator's original link no longer matches the stored hash.

**Evidenz**

- `backend/prisma/schema.prisma:38`: A single @unique passwortSetzenToken column (plus Ablauf on line 39). The comment on line 37 says it is the shared mechanism for Initial-Zugang and 'Passwort vergessen'.

- `backend/src/auth/auth.service.ts:54`: passwortSetzen looks up by the hash of the presented token (lines 51-53). The overwritten original token finds no row, so line 55 throws BadRequest 'Link ist ungültig oder abgelaufen.'
- `backend/src/nutzer/nutzer.controller.ts:13`: The only account-management routes are POST /nutzer (create) and GET/PATCH /nutzer/me. No route reissues an Initial-Zugang link.

## 2. Auth rate limit is keyed on the reverse-proxy peer address, so one anonymous client can block login, passwort-vergessen and passwort-setzen for every user

`backend/src/app.module.ts:ThrottlerGuard:shared-proxy-peer-tracker`

**Beschreibung.** The global ThrottlerGuard (app.module.ts:47) has no custom getTracker, so it uses the @nestjs/throttler default tracker, which is derived from the client IP (req.ips/req.ip). main.ts never sets Express 'trust proxy'. As a result req.ip is the TCP peer and X-Forwarded-For is ignored, which also means it cannot be spoofed. In the production topology (docker-compose.prod.yml) only Caddy publishes ports 80/443, and the Caddyfile reverse-proxies {$DOMAIN} to app:3000. The TCP peer for every public request should therefore be the Caddy container, so all users share one throttle bucket per handler. The storage is Redis, shared across instances. AUTH_THROTTLE (5 requests per 60 s) applies to POST /api/v1/auth/login, /passwort-vergessen and /passwort-setzen. An anonymous client sending about 5 requests per minute to one of these routes would get HTTP 429 returned to every other user of that route for the rest of the window. That includes first-time onboarding through the initial-access passwort-setzen link. All other handlers share one 60/min bucket per handler across the whole user base. The impact is availability only: there is no bypass of authentication and no disclosure. Code comments (auth-throttling-redis.e2e-spec.ts:56, 'schlüsselt standardmäßig nach Client-IP') show the intended design is a per-client limit. The dev compose publishes app:3000 directly and is not affected in the same way.

**Behauptete Ursache.** The throttler tracker falls back to the socket peer address because Express 'trust proxy' is not configured for the single known Caddy hop, and no getTracker override exists. Behind the reverse proxy, the intended per-client-IP limit collapses into one global quota per route handler.

**Trace**

- *entrypoint* `Caddyfile:7` ({$DOMAIN} site block): reverse_proxy app:3000: all public app traffic (anonymous internet) reaches the backend only through Caddy.
- *propagation* `backend/src/main.ts:9` (bootstrap): The Nest/Express app is created and configured (lines 9-16) without app.set('trust proxy', ...). req.ip is therefore the TCP peer (Caddy) and X-Forwarded-For is ignored.
- *propagation* `backend/src/app.module.ts:47` (AppModule providers): Global APP_GUARD ThrottlerGuard with the default IP-based tracker (no subclass or getTracker override anywhere in the repo). Throttle state is kept in Redis storage shared across instances (line 32).
- *sink* `backend/src/auth/auth.controller.ts:53` (AuthController.login): @Throttle(AUTH_THROTTLE) 5/60s is enforced against the tracker value, which is expected to be the same for all users, so one client exhausting it makes the guard return 429 to every login attempt in the window.

**Evidenz**

- `backend/src/app.module.ts:31`: Default throttler ttl 60000 and limit 60. ThrottlerModule options set no custom tracker or key generator.
- `backend/src/auth/auth.controller.ts:14`: AUTH_THROTTLE = { default: { limit: 5, ttl: 60_000 } }. It is applied at line 53 (login), line 76 (passwort-vergessen) and line 83 (passwort-setzen), all of which are public.
- `backend/src/main.ts:9`: No 'trust proxy' setting. A repo-wide grep (excluding .claude and node_modules) finds no 'trust proxy', trustProxy or getTracker.
- `docker-compose.prod.yml:15`: Only the caddy service publishes ports (80/443). The app service (lines 28-53) has no ports, so public requests reach it only via Caddy on the compose network.
- `Caddyfile:7`: reverse_proxy app:3000 with default header handling. Caddy sets X-Forwarded-For, which the app does not trust.
- `backend/test/auth-throttling-redis.e2e-spec.ts:56`: A comment states that the tracker is intended to key by client IP, which confirms the per-client design intent that the proxy topology defeats.
- `backend/package.json:37`: @nestjs/throttler ^6.7.0. Its default tracker is IP-based. The exact installed version cannot be verified locally because node_modules is absent.

**Blocker**

- No target execution is permitted in this run: node_modules is absent, installs are prohibited, and there is no OS-enforced sandbox. So no local NestJS fixture can be run to observe the tracker key and a 429 for a second client, and the @nestjs/throttler default getTracker cannot be read from the installed package.
- Deployment fact that is not visible in source: the remote address Node sees for requests proxied by Caddy on the production compose network. It is expected to be the single Caddy container IP for every client.

## 3. Wareneintrag multipart parser does not limit the number or total size of text fields it buffers in memory

`h3-input:wareneintrag-multipart-unbounded-fields`

**Beschreibung.** POST /api/v1/wareneintraege and PATCH /api/v1/wareneintraege/:id use FileFieldsInterceptor with memoryStorage(), and the only limit set is limits.fileSize (10 MB). Unless the multer version in the lockfile (2.4.0) sets its own defaults, busboy 1.6.0 defaults apply to non-file parts: fields=Infinity, parts=Infinity, fieldSize=1 MiB. Multer then appends every text field to req.body inside the one shared Node process. ValidationPipe (whitelist + forbidNonWhitelisted) only rejects the unknown keys after multer has finished parsing the whole body. The global ThrottlerGuard and JwtAuthGuard (JWT cookie + CSRF double submit) run before the interceptor, so the attacker needs a Nutzer session. By design, any Nutzer can create further Nutzer accounts. One such request carrying many ~1 MiB text fields grows the heap roughly in proportion to the body size. The repository sets no body cap in Caddy, no Node heap flag and no container memory limit, so one large enough body could exhaust the heap of the single app instance. Every Nutzer would lose service until Docker's restart: unless-stopped brings the app back. Whether heap exhaustion is actually reached depends on the installed multer defaults and on deployment memory, proxy and timeout facts that cannot be observed here.

**Behauptete Ursache.** FOTO_UPLOAD_OPTIONS (backend/src/wareneintrag/wareneintrag.controller.ts:38) sets limits: { fileSize } only. It sets no fields, fieldSize, parts or files limit, so text parts are not bounded in total. No upstream request-body cap exists in the Caddyfile, and the Dockerfile and prod compose set no heap or memory limit.

**Trace**

- *entrypoint* `backend/src/wareneintrag/wareneintrag.controller.ts:115` (WareneintragController.create (POST /api/v1/wareneintraege)): Authenticated multipart POST. The class-level JwtAuthGuard (line 82) and the global ThrottlerGuard (60/min) run before the FileFieldsInterceptor, so a Nutzer session plus a CSRF token is required. PATCH :id (line 126) uses the same interceptor options.
- *propagation* `backend/src/wareneintrag/wareneintrag.controller.ts:38` (FOTO_UPLOAD_OPTIONS): The multer options are memoryStorage() with limits: { fileSize: 10 MB } only. No fields/fieldSize/parts/files limit is passed, so the busboy 1.6.0 defaults (fields and parts Infinity, fieldSize 1 MiB) govern text parts, unless multer 2.4.0 adds its own defaults.
- *sink* `backend/src/wareneintrag/wareneintrag.controller.ts:119` (@Body() dto populated from multer req.body): Multer has already appended every text field to req.body in process memory by the time the handler's parameters are resolved. ValidationPipe forbidNonWhitelisted (main.ts:15) rejects the extra keys only afterwards, so the memory stays held for the whole request.

**Evidenz**

- `backend/src/wareneintrag/wareneintrag.controller.ts:38`: const FOTO_UPLOAD_OPTIONS = { storage: memoryStorage(), limits: { fileSize: FOTO_MAX_GROESSE_BYTES } }; is the only multipart limit configured anywhere in the source (a grep finds no MulterModule.register or other multer config).
- `backend/src/wareneintrag/wareneintrag.controller.ts:36`: The comment states the intent to abort oversized uploads instead of buffering them in RAM, but the configured bound covers only file parts.
- `backend/package-lock.json:6398`: The lockfile pins multer 2.4.0 (and busboy 1.6.0 at line 3953). Whether this multer version adds default field/part limits cannot be checked because node_modules is absent.
- `Caddyfile:7`: reverse_proxy app:3000 has no request_body max_size directive, so the ingress sets no body-size cap.
- `backend/src/main.ts:15`: The global ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }) runs after the interceptor has fully parsed the multipart body.
- `docker-compose.prod.yml:30`: The app service has restart: unless-stopped and no mem_limit or deploy resources. The Dockerfile (CMD node dist/main.js, line 49) sets no --max-old-space-size or NODE_OPTIONS. There is a single app instance.

## 4. Wareneintrag freitext has no maximum length, so one Nutzer can store roughly 1 MiB entries that every other Nutzer's default list view downloads and renders

`h3-input:wareneintrag-freitext-unbounded-length`

**Beschreibung.** CreateWareneintragDto and UpdateWareneintragDto check freitext only with @IsString and @MinLength(1) and have no @MaxLength. POST and PATCH /api/v1/wareneintraege are parsed by FileFieldsInterceptor with limits set to { fileSize } only (controller.ts:38). Text fields therefore fall back to the multer 2.4.0 / busboy 1.6.0 default fieldSize, which is 1 MiB according to the lockfile versions. The global ValidationPipe (main.ts:15) does not bound them either. The value is stored as-is in a TEXT column (migration 20260918130318). The generated to_tsvector column does not reject repetitive text, although diverse text near 1 MiB may exceed the tsvector size limit and fail the insert. Any authenticated Nutzer can read all entries by design. GET /api/v1/wareneintraege (listeAlle findMany, and the raw full-text path) returns the full freitext of the newest entries: 20 by default in the frontend (wareneintrag-liste.ts:70) and up to 100 via proSeite. The Angular list renders every freitext in full (wareneintrag-liste.html:97). So 20 entries of about 1 MiB from one Nutzer make every Nutzer's default list load serialize, transfer and render about 20 MiB (about 100 MiB at proSeite=100). This lasts until the author deletes them, because only the author may delete or edit (pruefeBesitz) and there is no admin path in the app. The attacker must be authenticated and is attributable through erfasstVon. The impact is persistent degradation of backend memory/bandwidth and of other users' (often mobile PWA) clients. It is not cross-tenant data exposure.

**Behauptete Ursache.** freitext has no upper length bound in CreateWareneintragDto/UpdateWareneintragDto and no multer limits.fieldSize (only limits.fileSize), while the shared list responses and the list UI embed and render freitext in full for every Nutzer.

**Evidenz**
